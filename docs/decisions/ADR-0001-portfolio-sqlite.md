# ADR-0001: 포트폴리오 전환 — 실서버(HANA + Service Layer)를 자체 SQLite + ERP 엔진으로 대체

- 날짜: 2026-08-14
- 상태: 채택

## 맥락

이 프로젝트를 **공개 포트폴리오로 내보내기로** 했다. 초기 개발은 SAP B1 실서버(HANA 조회 +
Service Layer 쓰기)에 붙여 진행했지만, 공개하려면 그 전제를 걷어내야 한다:

1. 실서버에 의존하면 접속 좌표와 실제 업무 데이터가 저장소에 딸려 들어간다.
2. 공개 배포(Vercel)와 자동 CI 가 필요하다.
3. 클론한 사람이 계정·VPN·환경변수 없이 바로 실행할 수 있어야 한다.

## 결정

데이터 계층을 **SQLite(better-sqlite3) + 결정적 가상 시드**로 교체하고, 쓰기 경로는
**로컬 ERP 엔진**으로 대체한다. 화면·액션·컴포넌트 계층은 손대지 않는다.

> 📌 **후속**: 드라이버는 [ADR-0002](ADR-0002-shared-db-turso.md) 에서 `better-sqlite3` → `libsql`
> 로 교체했다(서버리스 쓰기 영속을 위한 원격 공유 DB 지원). 아래 설계는 그대로 유효하고,
> 바뀐 것은 ① 커스텀 스칼라 함수를 SQL 재작성으로 옮긴 것 ② 트랜잭션 중첩을 SAVEPOINT 로
> 명시한 것 둘뿐이다.

### 1. HANA 호환 계층 — 화면 쿼리를 고치지 않는다

화면 30여 개가 HANA 문법(`SELECT TOP n`·`TO_VARCHAR`·`TO_DECIMAL`·`DAYS_BETWEEN`)으로
쿼리를 쓴다. 이걸 전부 SQLite 문법으로 고치면 수백 줄의 diff 가 생기고, 각 화면마다 회귀 위험이
생긴다. 대신 어댑터(`src/lib/db/sqlite.ts`)에서:

- `db.function()` 으로 `TO_VARCHAR`·`TO_DECIMAL`·`DAYS_BETWEEN` 을 등록해 **HANA 함수를 그대로 제공**
- `SELECT TOP n` → `SELECT … LIMIT n` 재작성 (중첩 TOP 은 조용히 변환하지 않고 명시적으로 거부)

결과: 화면 쿼리 **한 줄도 수정하지 않았다.** 게이트웨이(`hana.ts`)의 공개 인터페이스
(`query`/`queryOne`·read-only 가드·`ReadOnlyViolation`)도 그대로 유지했다.

### 2. 저장 프로시저 → TS 재구현

SQLite 엔 저장 프로시저가 없다. `CF_STOCK`(창고별 재고 / 재고전기리스트)을
**결과셋 계약 그대로** TS 로 재구현했다(`src/lib/db/procImpl.ts`). 계약에는 비직관적인 부분이
있고 그대로 지켰다 — 수량 컬럼은 **콤마 포맷 문자열**, 소계행은 `DOCENTRY=''`.
호출부(`callProc`)와 이를 쓰는 두 화면(창고 재고 조회·재고 이동 내역)은 무수정이다.

### 3. Service Layer → 로컬 ERP 엔진

`src/lib/sl/documents.ts` 의 **페이로드 타입(SL 계약)은 그대로 두고** 실행부만
`localErp.ts` 로 바꿨다. 엔진이 재현하는 업무규칙:

- 문서연결(draw): base 라인에서 품목·단가·창고·세금그룹 복사, `OpenQty` 차감,
  전량 이월 시 `LineStatus='C'`, 전 라인 마감 시 헤더 `DocStatus='C'`
- 미결수량 초과 이월 거부 · 거래처 불일치 거부 · 취소 문서 참조 거부
- 취소: 후속 문서 있으면 거부, 취소 시 base 미결수량 복원 + 재고 역분개
- 재고: 납품(-)/입고(+) 시 `OINM` 원장 + `OITW`/`OITM` 갱신, 약정·발주잔량은 열린 오더에서 재계산
- 분개: 납품·송장 전기 시 `OJDT` 생성 + 헤더 `TransId` 연결

**전환 전에는 검증할 수 없던 것이 지금은 검증된다.** 원본 환경에서는 전기기간 잠금·실서버
제약 때문에 쓰기 경로를 자유롭게 돌릴 수 없었는데, 이제 문서흐름 왕복이 스모크로 상시 검증된다.

### 4. 시드는 엔진을 통해 생성한다

시드 생성기가 문서를 SQL 로 직접 INSERT 하지 않고 **엔진을 호출해** 만든다
(구매오더→입고→A/P송장, 판매오더→납품(부분)→A/R송장, 일부 취소까지). 그래서 `OpenQty`·
`LineStatus`·`DocStatus`·Base 체인·재고원장·분개의 정합이 계산이 아니라 **구성으로** 보장된다.
시드가 곧 엔진 통합 테스트다.

## 결과 (트레이드오프)

- **얻는 것**: 클론 → `npm install` → `npm run dev` 로 끝. 환경변수 0개. 쓰기 경로가 실제로
  동작해 데모에서 문서 생성·문서연결·취소를 직접 해볼 수 있다. 스모크 27항목이 상시 검증한다.
- **포기하는 것**: 실 SAP 의 검증 로직(재고 마이너스 정책·전기기간·승인 워크플로 등)은 재현
  범위 밖이다. 엔진은 화면이 의존하는 규칙만 구현한다.
- **주의**: 서버리스(`:memory:`)는 인스턴스마다 독립이라 배포 데모에서 쓴 데이터는 인스턴스
  수명만큼만 유지된다. 영속이 필요해지면 Turso/Postgres 로 바꾸되 교체 지점은
  `src/lib/db/sqlite.ts` 하나다.

## 검토한 대안

- **화면 쿼리를 SQLite 문법으로 전부 수정** — 탈락: 30여 파일 대량 diff + 화면별 회귀 위험.
  어댑터 한 곳에서 흡수하는 편이 안전하고 되돌리기도 쉽다.
- **쓰기 경로를 막아두기(읽기 전용 데모)** — 탈락: 이 프로젝트의 핵심 가치가 문서흐름 구현인데
  그걸 못 보여준다.
- **JSON 픽스처** — 탈락: SQL 계층과 프로시저·집계 쿼리를 통째로 버리게 된다.
