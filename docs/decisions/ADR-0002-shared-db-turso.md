# ADR-0002: 서버리스 쓰기 영속 — 드라이버를 libSQL 로 바꾸고 공유 DB(Turso)를 붙인다

- 날짜: 2026-08-19
- 상태: 채택
- 관련: [ADR-0001](ADR-0001-portfolio-sqlite.md)

## 맥락

ADR-0001 로 데이터 계층을 SQLite + 가상 시드로 바꾸면서, 서버리스에서는 DB 가 인스턴스
메모리(`:memory:`)에 떴다. 조회 데모로는 문제가 없지만 **쓰기 데모가 성립하지 않는다** —
문서를 만들어도 다음 요청이 다른 인스턴스로 가면 사라진다. 이 프로젝트에서 가장 보여주고
싶은 것이 문서흐름(오더 → 납품 → 송장)의 쓰기인데, 라이브 데모에서 그게 안 보였다.

## 결정

**드라이버를 `better-sqlite3` → `libsql` 로 교체하고, `TURSO_DATABASE_URL` 이 있으면
원격 공유 DB 를 정본으로 쓴다.** 데이터가 인스턴스 밖에 있으므로 쓰기가 남는다.

### 왜 `libsql`(동기 드롭인)인가 — `@libsql/client`(비동기)가 아니라

`@libsql/client` 는 `execute`/`batch`/`transaction` 이 전부 Promise 다. 우리 ERP 엔진
(`src/lib/sl/localErp.ts`)은 **동기 트랜잭션 덩어리**다 — 문서 하나를 만들 때 헤더·라인·
재고원장·분개·원천 미결수량을 한 트랜잭션으로 처리한다. 비동기 클라이언트로 가면 엔진
호출부 66곳과 트랜잭션 5개를 전부 async 로 훑어야 하고, 서버 액션·시드·스모크까지 번진다.

`libsql` 패키지는 better-sqlite3 호환 **동기** API 를 제공하면서 원격 URL 을 받는다.
실측으로 `prepare`·`transaction(fn)`·롤백·`pragma`·다중문 `exec` 가 전부 동작했다.
→ **엔진·시드·프로시저 재구현은 한 줄도 고치지 않았다.**

### 그 대신 감수한 두 가지

**① 커스텀 스칼라 함수를 못 쓴다.** `db.function()` 은 타입 정의에는 있지만 런타임에
`not implemented` 로 던진다(원격은 애초에 SQL 이 서버에서 실행되니 JS 함수를 심을 자리가
없다). 우리는 HANA 호환을 위해 `TO_VARCHAR`·`TO_DECIMAL`·`DAYS_BETWEEN` 을 등록해
화면 쿼리 99곳에서 썼다.
→ **SQL 재작성으로 옮겼다**(`translateHanaSql`). 이미 `SELECT TOP` → `LIMIT` 재작성기가
있던 자리다. 인자에 괄호가 들어간 중첩 호출(`TO_DECIMAL(COALESCE(…),19,2)`)이 있어
정규식으로는 안 되고 괄호 짝을 맞추는 파서를 넣었다. **화면 쿼리는 여전히 무수정이다.**

| HANA | 치환된 SQLite |
|---|---|
| `TO_VARCHAR(d,'YYYY-MM')` | `substr(d,1,7)` |
| `TO_VARCHAR(d,'YYYYMMDD')` | `replace(substr(d,1,10),'-','')` |
| `TO_DECIMAL(v,p,s)` | `CAST(v AS REAL)` |
| `DAYS_BETWEEN(a,b)` | `CAST(julianday(substr(b,1,10)) - julianday(substr(a,1,10)) AS INTEGER)` |

**② 트랜잭션 중첩이 안 된다.** libSQL 은 `BEGIN` 중첩을 거부한다
(`cannot start a transaction within a transaction`). better-sqlite3 는 중첩을 감지해
자동으로 SAVEPOINT 를 썼고, 그 덕에 "시드(바깥 트랜잭션)가 ERP 엔진(안쪽 트랜잭션)을
호출"하는 우리 구조가 그냥 돌았다.
→ `runInTransaction(db, fn)` 을 만들어 **이미 트랜잭션 안이면 SAVEPOINT 로 중첩**한다.
원자성 의미는 종전과 같다.

### 시드는 로컬에서 만들어 통째로 밀어 넣는다

원격 커넥션에 시드를 그대로 태웠더니 **10분이 지나도 끝나지 않았다.** 시드는 엔진으로
문서를 200여 건 만드는 작업이라 문장이 1,300개가 넘고, 왕복 지연이 전부 곱해진다.
→ `npm run turso:reset` 은 ① 메모리 DB 에 0.3초 만에 시드하고 ② SQL 로 덤프해
③ 400문장씩 묶어 보낸다. **25초**로 줄었다.

같은 이유로 **앱은 원격을 자동 시드하지 않는다.** 콜드스타트마다 시드가 돌면 함수
타임아웃이고, 동시 콜드스타트가 겹치면 경합한다. 시드·초기화는 리셋 스크립트 전담이다.

### 공유 DB 는 매일 초기화한다

배포본은 **모든 방문자가 같은 DB** 를 본다. 데모로 만든 문서·취소 흔적이 쌓이면 README 에
적힌 수치(매출 15,803,260 등)·스크린샷과 어긋나고, 마음먹으면 데이터를 비울 수도 있다.
→ GitHub Actions 크론이 매일 03:00 KST 에 `turso:reset` → `turso:verify` 를 돌린다.
점검은 화면이 쓰는 조회 경로로 하므로 "돌았다"가 아니라 "맞게 들어갔다"까지 본다.

## 결과

- 로컬(파일)·테스트(메모리)·배포(공유 DB)가 **같은 코드 경로**를 탄다. 분기는 접속 대상뿐이다.
- 스모크 51항목 통과 — 수치도 종전과 동일(매출 15,803,260 · 재고 15,584 · 매입 21,095,976).
- 원격 실측: 화면 쿼리·`CF_STOCK`·HANA 함수 3종 정상, 문서 생성 1.4초, 취소·복원 정상.
- `TURSO_DATABASE_URL` 이 없으면 종전과 똑같이 동작한다(클론 즉시 실행 성질 유지).

## 대안과 기각 이유

| 대안 | 기각 이유 |
|---|---|
| `@libsql/client`(비동기)로 전환 | 엔진 66곳·트랜잭션 5개를 async 로 전환해야 한다. 얻는 것 없이 회귀 위험만 커진다 |
| Postgres/RDS 등 다른 DB | 화면 쿼리가 HANA/SQLite 문법 전제다. 방언이 또 달라지면 재작성기를 새로 써야 한다 |
| 쓰기만 별도 API 로 분리 | 엔진을 둘로 쪼개는 셈이라 "쓰기는 엔진 한 통로" 원칙이 깨진다 |
| 초기화 없이 방치 | 데모 데이터가 오염돼 README·스크린샷과 어긋난다 |
